# 4. Meshes and static fields

## 4.1 The registered meshes

The port runs **registered** meshes: each entry in the registry
(`src/hexcore/drivers/mpas_mesh_binding.py`) declares the mesh's shape, its file digests,
and its admitted timestep, and a forecast binds the named mesh against the
real files before anything touches the GPU. An unregistered mesh, a wrong
name, or a swapped file is refused by name: the registry runner's
`--selftest` proves all three refusal directions on demand.

The registry holds **21 rows** at this release: the two published NCAR
meshes, one generated uniform global mesh, twelve generated graded
(variable-resolution) global meshes, and six limited-area culls. Between
them they declare five timesteps (120, 100, 75, 60 and 20 s) each admitted
against its own file's `dcEdge`. There is no `--list` flag; a wrong `--mesh`
name prints the whole set, which is how you read it. The registry ships in
the package (`woof/hex/drivers/mpas_mesh_binding.py`), so this works from an
install:

```sh
woof hex forecast --mesh nope --grid x --static y --init z --out out
```

```
woof hex: --mesh 'nope' is not a registered mesh.  Registered meshes are
conus-x1.2971, r4.75.11020, r4.75.14050, r4.75.15755, r4.75.4440, r4.75.7975,
u96.64002, v15.150.38857, v15.60.224197, v15.60.224210, v16.66.195629,
v16.66.195630, v20.80.151649, v4.75.121182, v4.75.123423, v4.75.128019,
v6.75.112676, v6.75.114257, v6.75.120989, x1.40962, x4.163842.  A row pins its
grid and static by byte count and SHA-256 and declares the timestep its real
dcEdge admits; running an unregistered mesh would run an unproved shape at an
unadmitted timestep.  Register the row in src/hexcore/drivers/mpas_mesh_binding.py before
running it.
```

The rows this manual works from, and what each one is for:

| mesh | cells | spacing | dt | provenance of the static | forecast status |
| --- | --- | --- | --- | --- | --- |
| `x1.40962` | 40,962 | ~120 km uniform | 120 s | native `init_atmosphere` v8.2.0 (NCAR-published) | proven green (this manual's quickstart ran it) |
| `x4.163842` | 163,842 | 92→25 km variable | 120 s | native `init_atmosphere` v8.4.1 | full-physics consistency and hex self-reproducibility reference; not a native dry-step agreement test |
| `u96.64002` | 64,002 | ~96 km uniform | 120 s | generated: `rw_mpas_mesh` GP(80,0) + unified `rw_mpas_static` | proven green, the first generated mesh to complete a full-physics forecast |
| `v20.80.151649` | 151,649 | 20 km in 80 km graded | 120 s | generated: hierarchical Goldberg ladder + unified `rw_mpas_static` | proven green, 6 h full physics; regenerates bit-identical to its registered bytes |
| `v16.66.195629` | 195,629 | 16.5 km in 66 km graded | 100 s | as above | proven green, 36/36 steps at 100 s, the finest graded mesh to complete a forecast |
| `v15.60.224210` | 224,210 | 15 km in 60 km graded | 75 s | as above | the largest mesh here; admitted on device memory through the real door, no forecast run |
| `v15.150.38857` | 38,857 | 15-km box in ~136 km | 60 s | generated by the unified writer `rw_mpas_static` | **refused at bind**: collapsed dual edges, see 4.5; its 60 s also holds no anchor |

Three admissions run at bind, all geometry-bound and all before CUDA
allocation. A fourth check, separate from geometry, asks whether the row's
declared timestep holds an EARNED anchor: `woof.hex.dt_admission` carries
five, and a row declaring anything else is refused by name (chapter 6).

**Timestep admission** checks the declared `dt` against the static file's own
complete `dcEdge` array (`dt <= 0.90 * min(dcEdge) / 125 m/s` for the outer
step; `src/hexcore/timestep_admission.py`). An unsafe declaration is
refused with the actual minimum edge length, the requested dt, the computed
bound, and the remedy: it is never silently reduced. The quickstart's bind
line shows the gate working:
`min(dcEdge)=97076.508 m; dt=120.000 s; limit=698.951 s`.

**Dual-edge admission** checks `min(dvEdge/dcEdge)` against a floor of 0.02
(`src/hexcore/dual_edge_admission.py`). The TRiSK tangential operators
divide by `dvEdge` (`pv_apvm_v841_f32` forms
`grad_pv_tangential = Δpv / dvEdge`) so a mesh with a collapsed Voronoi
edge amplifies a tangential gradient by `dcEdge/dvEdge` and blows up inside
the first outer step no matter what timestep is declared. The floor is one
number for every row with no per-row override, sitting between the roughest
published reading (`x4.163842` at 0.033650) and the measured generated-mesh
dislocation class. Bind prints the reading, here for `u96.64002`:
`min(dvEdge/dcEdge)=0.394671 at edge 6 (dvEdge=32955.613 m), TRiSK
tangential amplification 2.534x; floor 0.02`.

**Cell-coordination admission** checks that no cell carries fewer than five
edges (`src/hexcore/cell_coordination_admission.py`) and records the whole
histogram either way. A Goldberg polyhedron has pentagons and hexagons; a
four-sided cell is a generator defect that no closure invariant detects, and
one of them killed a forecast with a ~197 K standing error at model top.
The floor is one-sided on purpose, only coordination below five refuses,
because an 8-coordinated cell was measured NOT to misbehave and a gate with
no measured breakage behind it is not a gate (4.5).

## 4.2 Validate a pair: `woof hex mesh-check`

Run this before anything expensive touches a mesh:

```sh
woof hex mesh-check --grid assets/x1.40962.grid.nc --static assets/x1.40962.static.nc
```

It prints a JSON receipt, dimensions, connectivity indexing, and the
SHA-256 of both files (chapter 2 shows the output), and refuses a
defective or mismatched pair by name. The digests it prints are what the
registry pins, so `mesh-check` is also how you confirm your copy of a
registered mesh is the registered bytes.

A regional (limited-area) cull carrying the `bdyMaskCell/Edge/Vertex`
triple is validated against the regional contract (sentinel-tolerant
connectivity keyed to the seven boundary rings, Euler characteristic 1 for
a disk, and the mask-derivation rules) and the receipt gains a `regional`
block: zone width, per-ring cell counts, and the `bdy_mask_sha256` a
regional registry row pins. A culled grid exists before its static does,
so `mesh-check --grid-only --grid <file>` validates the grid alone; the
receipt records `static: null` and any `--static` is not read in that
mode.

## 4.3 Generate a mesh and its static: `woof mesh`

New meshes come from the **engine's** door, `woof mesh`: it generates an
icosahedral Goldberg grid at the resolution you ask for and builds the
matching static in the same run, with no native toolchain anywhere in the
loop. (This door was not present on the published gpuwm 2.5.2 wheel; it
arrives with the 2.5.3 bundle, well below the floor this distribution's
declared `gpuwm>=2.9.12,<2.10` range requires. The commands below were proven from a `woof` checkout.)

**See what a card can hold:**

```sh
woof mesh --list-cards
```

```
cards in <woof>/data/mpas/mesh-sizing.json
  rtx-3080       NVIDIA GeForce RTX 3080 (10 GiB)
                 NOT MEASURED -- NOT MEASURED. No full-physics footprint run has been made on this part.
  rtx-5070-ti    NVIDIA GeForce RTX 5070 Ti
                 15,881 MiB (addressable); 70 SM x 1536 threads
                 model 5,384 MiB fixed (2,896 derived store + 2,488 measured residue) + 86,630 B/cell; holds 127,051 cells
                 anchor x1.40962: 40,962 cells measured at 8,768.0 MiB
  rtx-5090       NVIDIA GeForce RTX 5090
                 32,607 MiB (nvidia-smi total, NOT MEASURED through CUDA); 170 SM x 1536 threads
                 model 9,798 MiB fixed (7,032 derived store + 2,766 measured residue) + 86,630 B/cell; holds 276,081 cells
                 anchor generated: 38,857 cells measured at 13,165.0 MiB
                 anchor x1.40962: 40,962 cells measured at 13,182.0 MiB
                 anchor x4.163842: 163,842 cells measured at 23,334.0 MiB

smoothness bound (provisional): refuse above 3.06 %/cell, published reference 1.53 %/cell
```

**Those rows are the ENGINE's own sizing table, not the port's admission
model, and the two must not be averaged.** They are a line in cell count
(`fixed + slope × cells`) whose anchors predate the port's frame cut; the
port's gate has a different shape and different numbers (4.6). Use this
table to size a mesh at `woof mesh` and 4.6's model to decide whether the
result will run.

**Size a request without writing anything:**

```sh
woof mesh --refine 39.1,-84.5,800,25 --background-km 92 --card rtx-5070-ti --dry-run
```

This asks for a 25-km circle of radius 800 km centered at 39.1N, 84.5W in a
92-km background (the same refinement ratio as the published `x4` family)
sized to fill an RTX 5070 Ti. The dry run prices it at 127,051 cells with a
1.65 %/cell steepest spacing gradient and applies both gates (device budget
and mesh smoothness) before you spend a minute of compute.

Ask for something too steep and the door refuses with the mechanism and the
remedy: this run was kept because the refusal is the door working:

```sh
woof mesh --refine 39.1,-84.5,300,15 --background-km 120 --card rtx-5070-ti --dry-run
```

```
woof mesh: REFUSED: the requested mesh is 4.32 %/cell at its steepest spacing
gradient, past the 3.06 %/cell this release will emit.
  what breaks: A mesh whose cell size jumps faster than the numerics were designed
  for degrades the C-grid gradient and divergence operators across the transition
  band: the errors show up as a standing wave parked on the refinement boundary,
  which looks like weather and is not.
  what to change: widen the transition (a fifth field on --refine, in km), coarsen
  the refinement, or refine a smaller area.  --allow-rough-mesh emits it anyway and
  is reported as a workaround.
```

### A `--spec` request has its own door: `woof hex mesh-plan`

`woof mesh --refine` applies its own smoothness gate at `--dry-run`, shown
above. A `--spec` JSON handed straight to `rw_mpas_mesh --dry-run` does not
get that: the generator sizes the request, prints a receipt and exits 0
without applying either gate its own build applies. Two designs measured
2026-08-28 on the current engine:

* a 0.75/6/75 km design sized clean and the build refused it 87 ms later on
  the transition-band gate: arithmetic on the same steepest-gradient
  number the dry-run receipt had just printed;
* a 0.75/3/15/75 km design sized clean, cleared that gate, relaxed 220,468
  cells for **711 s** and was then refused on the 200 m shortest-dual-edge
  floor, with no grid written.

`woof hex mesh-plan` closes the first and names the second, in about a
fifth of a second:

```sh
woof hex mesh-plan --spec my-case.json --card rtx-5070-ti
```

#### Where that gradient is measured (changed 2026-08-29)

The transition-band gate is arithmetic on one number, and until 2026-08-29
the generator sampled that number on a lattice spread evenly over the whole
globe. At the 50,000 points it used, those sit about 101 km apart, so a
refinement transition narrower than that was stepped over entirely and the
receipt reported the flat background the lattice happened to land on. On an
eight-rung 51.2 km to 200 m ladder it printed 12.12 %/cell for a field that
reads 37.04, and the build admitted a design its own gate exists to refuse.
Nothing in the reading said so, because a maximum over points that missed the
ramp looks exactly like a gentle ramp.

The generator now probes where a spec says its regions are (a shell a few
transition widths wide around each region boundary, resolved across the ramp
rather than along it) and prints two more fields beside the number:
`gradient_probe_points`, what the reading cost, and
`gradient_probe_coverage`, which reads `complete` when every locus where the
field varies was covered. `woof hex` refuses to judge a spec on a receipt
that does not say `complete`, including a receipt from an older engine that
does not say anything, because a number that is not a measurement is not
something to gate on.

Two consequences worth stating plainly. Specs with ramps hundreds of
kilometres wide (every swath the threat metrics emit, and the two examples
above) do not move: the old lattice already resolved them, and their
readings shift in the fourth decimal. Specs with sub-kilometre cores and
short ramps do move, sharply, and some designs that used to build now refuse
before anything is seeded. That is the gate working, not a new restriction:
the band was always that narrow.

And what still is not measured this way: `predicted_cells` and
`region_attainment` on the same receipt are still integrals over the global
lattice, with the resolution limit that implies. Only the gradient follows
the regions.

It prices the spec through the generator's own sizing integral, applies the
transition-band gate here (so a spec the build would refuse is refused
before the build, with the ramp widening that clears it quoted in the spec's
own units), and prints the shortest-dual-edge floor as what it is: a gate
that reads the finished tessellation, cannot be decided from a spec, and is
predicted (never refused) from the generator's own 0.04 surgery flag
floor. A finest spacing under 5 km is where that prediction turns against
you. `--json` prints the whole receipt; `--out` writes it beside your case.


**Generate for real**: grid and static in one command. The proving run
built a small uniform demonstration pair (a resolution spec plus an explicit
cell count) in under three minutes end to end, the static half in 94.5 s
with its 82 variables:

```sh
woof mesh --out demo.grid.nc --background-km 480 --cells 2562 \
    --name manual-demo --geog <WPS_GEOG-root> --receipt demo.receipt.json
```

```
woof mesh: WROTE demo.static.nc 4908228 82 ea7cf7b3cf57...
woof mesh: wrote demo.static.nc (4,908,228 B, 82 variables, SHA-256 ea7cf7b3cf57...)
woof mesh: nominalMinDc 480,000.000000 m declared as FP32 0x48ea6000 -- the mesh
registry compares this scalar bit for bit
woof mesh: the pair is demo.grid.nc + demo.static.nc
```

A mesh needs both a **resolution** (`--background-km`, `--refine` rows, or
a `--spec` JSON) and a **size** (`--card NAME` to fill a card, or
`--cells N`); giving only one produces a named refusal pointing at the
other. The static lands beside the grid (`--static-out` to move it);
`--no-static` is a workaround, reported as one, because a lone grid file is
refused by the registry before any dycore sees it.

## 4.4 The geographical data the static is built from

The static builder samples a WPS-GEOG archive (terrain, land use, soil,
green-ness, albedo). The engine stages it:

```sh
woof fetch-geog --root <WPS_GEOG-root> --list     # what is staged / what would download
```

```
  staged  topo_gmted2010_30s: ... (~1798 MiB unpacked)
  staged  modis_landuse_20class_30s_with_lakes: ...
  staged  soilgrids: soilgrids.tar.bz2 824.1 MiB (~12530 MiB unpacked)
fetch-geog: total 2.01 GiB download, ~27.7 GiB unpacked
```

Drop `--list` to actually stage (the proving box's root was staged by this
command; `--datasets mesh` limits the set to what `woof mesh` needs). The
soilgrids archive is ~13 GiB unpacked and only the mesh door reads it.

**A known layout trap, stated so you do not lose an afternoon to it:**
`woof fetch-geog` stages the soilgrids datasets *nested*
(`WPS_GEOG/soilgrids/soilcomp`, `WPS_GEOG/soilgrids/texture_layer1`, …)
while `rw_mpas_static` resolves them *flat* (`WPS_GEOG/soilcomp`, …). On a
tree fetch-geog itself staged, the static build refuses naming five missing
datasets. The working layout on the proving machine bridges the gap with
directory junctions (symlinks on Linux) from the root to the nested copies:

```
WPS_GEOG/soilcomp        -> WPS_GEOG/soilgrids/soilcomp
WPS_GEOG/texture_layer1  -> WPS_GEOG/soilgrids/texture_layer1
...and texture_layer2..4, texture_top, texture_bot
```

This disagreement is a recorded cross-tool defect awaiting an engine-side
fix; until then the bridge above is the supported layout.

## 4.5 What a generated mesh is good for today: the exact boundary

**A uniform generated mesh forecasts.** `u96.64002` is ours end to end (grid
from `rw_mpas_mesh`, static from `rw_mpas_static`, init from `woof hex init`
with no native binary at any stage) and it completed a full-physics
forecast on an RTX 5070 Ti at `rc 0`, `status "passed"`, with
`finite: true` in every step's health record.

**A graded generated mesh forecasts too.** A graded global mesh comes from
a JSON spec, a background spacing plus any number of refinement regions
(cap, lat/lon box, polygon), at any ratio, at any coordinates, with no code
path per spec. The mechanism is a hierarchical Goldberg ladder: level 0 is
the same icosahedral subdivision the uniform arm uses, each level halves the
spacing by count-targeted midpoint insertion, and the transition annuli are
drained by count-changing defect surgery. All three of the campaign's graded
spec rows regenerate clean, and `v20.80.151649` regenerates BIT-IDENTICAL to
its registered bytes, every cell centre, ring and edge length exactly equal,
so its completed 6 h full-physics forecast describes what the generator
emits today. Measured across ten
level runs and four generated meshes (3,374 to 224,210 cells),
`min(dvEdge/dcEdge)` lands between 0.0406 and 0.1023: two to five times the
admission floor, zero edges under 0.04 on any of them.

**Two real generator defects had to be fixed to get there, and both are
worth recognising.**

*A four-sided cell.* A Goldberg polyhedron has pentagons and hexagons and
nothing else. The defect surgery's insertion operator placed its new
generator on a near-cocircular quad's own circumcentre, where the new cell's
Delaunay ring is exactly the four quad cells, so it emitted a
QUADRILATERAL, then pinned it during the local polish. Nothing downstream
saw it, because a four-sided cell plus the two heptagons the same operation
makes leaves `sum(6 - nEdgesOnCell)` at exactly 12: Euler characteristic,
degree sum and sphere closure all read correct on an illegal mesh. One such
cell kills a forecast. `v16.66.195630` carries exactly one (cell 195615) and
the model's theta maximum parks on it at the top model level with a ~197 K
standing error, converged in the timestep: dead at step 23 of 36 at 100 s,
step 31 of 48 at 75 s, the same model time. `cell_coordination_admission`
refuses coordination below five at bind and stays, because the mesh it
refuses is still registered and still on disk; `v16.66.195629` is that same
spec row regenerated by the fixed generator, and it runs 36 of 36.

*A polygon region that refined the far side of the planet.* The engine's
polygon containment test accepted on `|winding| > pi`, which cannot tell a
point inside a ring on a sphere from a point whose ANTIPODE is inside it, so
every polygon refinement region refined a congruent ghost of itself on the
opposite hemisphere. The ghost's edge is a step and not a ramp, so the
spacing field fell from the region's spacing to the background across one
cell and the smoothness gate then refused every emitted spec. Fixing the
containment test cleared both symptoms.

**What is still refused, and why it is not gradedness.** `v15.150.38857`
came from the retired density-biased Fibonacci seed, which is
polycrystalline: it carries 3,447 heptagons beside 3,459 pentagons, and a
pentagon-heptagon quad is near-cocircular, so the Voronoi edge between its
two nearly-coincident vertices collapses, 6.51 m against a 38,658.7 m
`dcEdge`. That is the whole of the old step-0 `FloatingPointError`. The
TRiSK tangential terms divide by `dvEdge`, so the potential-vorticity
gradient across that one edge is amplified 5,935x; a per-launch probe puts
every runaway magnitude in the first outer step on it, and the first
non-finite value in the run is `exner` at a neighbouring cell. No timestep
is a lever against it. That seed is retired to a control instrument, but the
row it produced is the bytes that measured the cost, so it stays registered
and stays refused: the generator refuses to emit such a mesh and the bind
refuses to run one, each naming the measurement.

## 4.6 Capacity planning by card

**The footprint is not a line in cell count, and you cannot size a mesh with
a pocket calculator.** It has this shape:

```
peak = core(your card, your configuration)
     + Grell-Freitas workspace at min(cells, SMs x 4 x 64) columns
     + YSU workspace        at min(cells, SMs x 16 x 32) columns
     + bytes per cell x cells
```

The two workspace terms grow with your mesh until it is bigger than what
your card can hold in flight, and then they stop. On a 170 SM part those
knees are at **43,520 cells** and **87,040 cells**. Below them the marginal
cost of a cell is higher than the slope; above them it is the slope. A third
term, the RRTMG shortwave column chunk, is sized from the card's resident
threads and never grows with the mesh at all: 1,745.6 MiB on a 170 SM part,
872.8 MiB on a 68 or 70 SM part.

Measured anchors on an RTX 5090 (170 SM) at the merged tip: `x1.40962` (40,962 cells)
peaked at **8,874 MiB**; `x4.163842` (163,842 cells) at **20,446 MiB**. The
shaped row reproduces both exactly.

To size a mesh for a budget, ask the surface: it inverts the model by
bisection because there is no single slope to divide by:

```python
from woof.hex.device_admission import KNOWN_CARDS, model_for_card
model = model_for_card(KNOWN_CARDS["10gib-68sm"])       # or your own CardProfile
model.max_cells(int(9_097 * 1024**2))                   # 68440 cells admitted
model.required_bytes(40_962)                            # 6884963136 free bytes
```

**Ask the question in the configuration you mean to run.** `model_for_card`
takes the configuration second, and it defaults to `"global"`; a limited-area
question must say so or it is answered with the wrong core:

```python
cull = model_for_card(KNOWN_CARDS["10gib-68sm"], "limited-area")
cull.required_bytes(11_020)                             # 6979108286
cull.measured                                           # False -- DERIVED, labelled
```

This is not only a planning surface: it IS the admission gate. The forecast
door, `--preflight` and the driver's own floor all answer from it, and the
door reads your card's multiprocessor count at the moment of the decision
rather than assuming a 5090.

**The margin is not a flat number either.** It is your card's shortwave
workspace plus 11.2 MiB of instrument convention, and each part names what
it absorbs: `ShapedFootprintModel.margin_terms()`. It replaced a flat
512 MiB that named nothing and was measured 1,104 MiB short on a
limited-area cull.

**A limited-area run is a different configuration and carries its own core**,
because the regional device stack builds a padded atmosphere, two levels of
lateral-boundary state and 22 more kernels. At cull cell counts it is about
85 % mesh-independent, which is why a line in cell count over-predicted every
measured cull by 1.2-1.9 GiB. That core is currently an ENVELOPE over five
whole-device samples, not a per-allocation fit, and it over-predicts the
smallest cull by about 1.3 GiB.

**Graded meshes cost nothing extra.** Measured at the model's own protocol,
`v20.80.151649` (151,649 cells) comes in 0.22 % *under* prediction and its
per-allocation census is the uniform mesh's scaled by cell count. The
earlier instruction to size graded meshes with extra margin was installed for
a defect that does not exist and is retired.

- **12 GiB card**: DERIVED, NOT MEASURED, no 12 GiB card exists in the
  measurement fleet, and the answer moves with the card's SM count, so ask
  `model_for_card` with your own profile rather than reading a number off
  this page.  Quoted on the 170 SM measured row (the most conservative,
  because its core and its margin are the largest measured) a full
  12,288 MiB budget carries **57,433 cells**, and the published `x1.40962`
  global mesh needs 10,631 MiB of it (8,874 MiB predicted peak plus that
  card's 1,756.8 MiB margin).  A row derived for a smaller part is
  materially larger: an 84 SM card takes 89,472 cells at the same budget.
- **16 GiB card**: the quickstart's runs on an RTX 5070 Ti (this manual's
  proving card) integrated `x1.40962` full-physics with room to spare.
  That card has its own measured row and the door selects it from the
  card's own multiprocessor count, with no flag: a smaller part is no
  longer priced with a 5090's core.  `--device-fixed-mib` /
  `--device-bytes-per-cell` still exist for a card whose own
  `tools/device_memory_ledger/` run has been made, but they are an escape
  hatch now rather than the remedy of first resort.
- **32 GiB card**: `x4.163842` measured 20,446 MiB at the merged tip and
  admits at **about 21.7 GiB free** (that peak plus the card's own named
  margin, not a flat headroom) so in practice it remains a 32 GiB-card
  configuration: a 24 GiB part running a desktop rarely offers that.  At
  the free memory an idle RTX 5090 actually offered (31,642.6 MiB, measured
  2026-08-26) the shaped model
  carries **266,328 cells**, and the largest mesh this project has
  generated (224,210) admits with room.  Whether such a mesh RUNS is a
  separate question the same preflight answers, and the timestep is no
  longer one number: `woof.hex.dt_admission` holds five earned anchors
  (120, 100, 75, 20 and 5 s) keyed by the CONFIGURATION, the timestep
  together with the cumulus selection.  Rule of thumb `dt ≈ 6 × dx(km)`;
  `v16.66.195629` (16.5 km core) binds and steps at 100 s (chapter 6).

`woof mesh --card NAME` applies its own per-card measured table (the
`--list-cards` output above, with per-card anchors) when sizing a new mesh,
and `--vram-gib X` substitutes a budget for a shared card. The sizing table
and the footprint model above are two separate measurement sets: the
sizing table's anchors predate the current engine pin and are the more
conservative of the two; do not average them together.
