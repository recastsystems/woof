# Build recipe for the WRF reference binary

The executable that produced the reference stream for configuration
`10d6e178d96648e35b826217cc001a1f598232bf6ceabd9ce07074a1f65e2031`.

This document is the recipe the manifest's `build_recipe_sha256` pins: the
digest is the SHA-256 of this file's bytes. It is transcribed from the build
tree on the node the binary was built on, and every figure below was read off
that tree rather than recalled. The raw build artifacts stay on the node --
they are not redistributable and several are large -- so their digests appear
here instead, and a reader with access to the node can check this transcription
against them.

**The compiler is GNU, not Intel.** WRF `configure` option **34**
(*Linux x86_64 ppc64le, gfortran compiler with gcc (dmpar)*) selected
gfortran/gcc; Intel oneAPI supplies the MPI layer only. The binary's own
bytes carry exactly one compiler stamp, `GCC: (Ubuntu 15.2.0-16ubuntu1)
15.2.0`, and no Intel Fortran signature. (`strings` does surface the token
`ifort`, but only inside WRF's own identifiers -- `ifortbl`, the RUC LSM
vegetation table -- which is not a compiler stamp.)

This contradicts two places in the tree that describe the reference stack as
Intel `ifx`: [`VERIFICATION.md`](../VERIFICATION.md) section 2, and the header
comment of the configuration file this manifest is addressed by. The
discrepancy is recorded here rather than corrected there, deliberately: both of
those files are identity-bearing. The configuration file's SHA-256 *is* the
identity this manifest, the acceptance band, and the certification capsule are
all addressed by, and `VERIFICATION.md` carries the table the band anchors on.
Editing either to fix a prose claim would move a digest that a certification
chain depends on. The measured truth belongs in the receipt; the correction to
the prose is an owner call, not a receipt-lane one.

## Configuration

```
./configure
  Compiler choice: 34      # Linux x86_64 ppc64le, gfortran compiler with gcc (dmpar)
  Nesting option:  1       # basic
```

C dialect override `-std=gnu17` was applied for GCC 15 compatibility; it
appears in `CFLAGS_LOCAL` below.

Flags as written into `configure.wrf`:

```
SFC              = gfortran
SCC              = gcc
CCOMP            = gcc
DM_FC            = mpif90 -f90=$(SFC)
DM_CC            = mpicc -cc=$(SCC)
FCOPTIM          = -O2 -ftree-vectorize -funroll-loops
FCNOOPT          = -O0
FCDEBUG          =                       # empty: no -g, no traps, no bounds checks
FORMAT_FIXED     = -ffixed-form
FORMAT_FREE      = -ffree-form -ffree-line-length-none
BYTESWAPIO       = -fconvert=big-endian -frecord-marker=4
FCBASEOPTS_NO_G  = -w $(FORMAT_FREE) $(BYTESWAPIO) $(FCCOMPAT)
FCBASEOPTS       = $(FCBASEOPTS_NO_G) $(FCDEBUG)
CFLAGS_LOCAL     = -w -O3 -std=gnu17 -c
ARCH_LOCAL       = -DNONSTANDARD_SYSTEM_SUBR -DWRF_USE_CLM $(NETCDF4_IO_OPTS)
NETCDF4_IO_OPTS  = -DUSE_NETCDF4_FEATURES -DWRFIO_NCD_LARGE_FILE_SUPPORT
TRADFLAG         = -traditional-cpp $(NETCDF4_IO_OPTS)
CPP              = /lib/cpp -P -nostdinc
OMP / OMPCC      = (commented out -- no OpenMP; dmpar, MPI only)
```

netCDF4 with HDF5 compression and large-file support are both on. OpenMP is
off: the build is pure `dmpar`, which is why every run of this binary in
evidence is MPI-only with `OMP_NUM_THREADS=1`.

`configure` emitted one warning, recorded here because it is a real capability
difference rather than noise: *"The moving nest option is not available due to
missing rpc/types.h file."* The reference case uses static nests, so the
missing capability is not exercised.

## Build

```
./compile em_real
```

`Registry/Registry.EM` was copied to `Registry/Registry` by the compile script,
as WRF's build does normally. The build log records `V4.6.1`,
`git commit d66e442fccc04111067e29274c9f9eaccc3cef28`, `WRF_EM_CORE`, and
`WRFIO_NCD_LARGE_FILE_SUPPORT=1`.

## What this recipe does not claim

It does not claim the binary is reproducible from these settings. WRF built by
this toolchain has not been shown to be bit-reproducible across rebuilds, and
nothing here tests it. What the recipe pins is the stated provenance of one
specific executable whose digest is fixed; if a rebuild produced different
bytes, the digest -- not the recipe -- is what the comparison is bound to.

It also does not claim the tree was pristine. The tracked files match tag
`v4.6.1`, but the working tree carries untracked build products (generated
`Registry/Registry`, generated `.f90` from `.F`, object files, the logs above).
That is what an in-place WRF build always looks like.
